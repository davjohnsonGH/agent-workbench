# ADR-0002: PostgreSQL with Drizzle ORM

- **Status:** Accepted
- **Date:** 2026-09-22

## Context

ADR-0001 needs durable storage for artifacts, versions, lineage, agent runs,
and approvals. The data is relational (projects → artifacts → versions →
decisions) with some document-shaped parts (artifact content, run inputs).
Because the project is also a learning vehicle, the database layer should stay
close to SQL rather than hide it.

## Decision

- **PostgreSQL** as the primary datastore. It handles relational integrity and
  JSON documents (`jsonb`) in one system. It runs locally via
  `infrastructure/docker/docker-compose.yml` and in CI as a service container.
- **Drizzle ORM** for schema definition, queries, and migrations, isolated in
  the `@repo/db` workspace. The schema is TypeScript (`packages/db/src/schema.ts`).
  Migrations are SQL files generated by `drizzle-kit generate` and committed
  to `packages/db/migrations/`.
- **The `postgres` (postgres.js) driver.**
- **Status and enum-like columns are `text` with TypeScript enums**, not native
  Postgres enums, because native enums are hard to change once created.

## Consequences

- Queries read like SQL and the generated migrations are plain SQL, so it is
  easy to see what hits the database.
- Types flow from the schema to callers without a separate code-generation step.
- Schema changes need an explicit `db:generate` followed by a reviewed
  migration. CI applies all migrations to a fresh database on every run.
- The database does not enforce enum-like values. Application code (and later
  check constraints, if needed) must validate them.

## Alternatives considered

- **Prisma:** mature, but uses its own schema language and a heavier client,
  and hides more of the SQL.
- **Kysely:** an excellent type-safe query builder, but it has no schema
  definition or migration generation built in.
- **SQLite:** simpler for local development, but it would diverge from the
  production target and has weaker `jsonb` and concurrency support.
